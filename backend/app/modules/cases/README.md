# cases

Business domain. Public facade is `__init__.py` — the only import surface for other modules (ARCHITECTURE.md §6).

Owns the `cases` PostgreSQL schema: the Case Management Console (Epic 4.3) — a
single case model for every compliance-relevant event across the platform,
regardless of which epic raised it.

**Scope of this revision.** Only ANER-4.3-S1T1 (schema) and S1T2 (SLA
configuration and deadline calculation) are implemented. There is no `api/`
package, no event consumer, no assignment or resolution workflow, and no SLA
monitoring job — those belong to S2 and later stories.

## Boundary with `compliance.compliance_cases`

`compliance.compliance_cases` (compliance_0001) already exists and is not
touched by this module. It is a narrower, older mechanism: `AppendOnlyModel`
(a row's `status` can never change after insert), keyed only to
`payments.transactions`, with three statuses. It cannot represent an
onboarding review, a reconciliation break, or a webhook delivery failure —
closing that gap is what Epic 4.3 is for. The two modules define their own,
unrelated `CaseType` in their own schema; neither reuses or widens the other's.
Fully-qualify imports (`app.modules.cases` vs. `app.modules.compliance`) —
the class names collide across the two modules on purpose, not by
coincidence, and that is a real ongoing risk for anyone reading an
unqualified `ComplianceCase` or `CaseType` import in this codebase.

## Tables

### Case management (`cases_0001_case_management`)

| Table | Holds |
|---|---|
| `compliance_case` | one case, from any originating epic |
| `case_timeline_event` | the case's audit trail, in order. Append-only |
| `case_evidence_item` | evidence attached to a case |
| `case_sla_config` | GitOps-seeded SLA policy per (case_type, severity) |

## Invariants enforced below the application

**A duplicate originating event cannot create a duplicate case.**
`compliance_case.originating_event_id` is unique whenever it is not null (a
partial unique index, not a plain `UniqueConstraint` — a case with no single
originating event, e.g. `MANUAL`, must still be insertable with a null id).
This is the idempotency guard against a redelivered Kafka event creating a
second case for the same trigger.

**`case_reference` cannot collide, even under concurrent creation.**
Generated by a database trigger from a per-calendar-year counter table
(`case_reference_sequence`), advanced with a locked `UPSERT` inside the
inserting transaction — see the migration's module docstring for why this is
gap-free in a way a native `SEQUENCE` is not (a `SEQUENCE`'s counter does not
roll back with an aborted transaction; this counter does).

**A resolution needs a reason.** `resolution_action IS NOT NULL` requires a
non-empty `resolution_note`, checked by the database, not only by the service
that writes the row.

**Some facts, once recorded, do not move.** `compliance_case.id`,
`.case_reference`, `.created_at` are immutable from insert; `.resolved_at` and
`.resolved_by` may each be set once and never again.
`case_evidence_item.added_at` is immutable the same way. `case_timeline_event`
rejects `UPDATE` and `DELETE` outright — it is a case's audit trail, not a
mutable log.

**A config redeploy never rewrites an open case's SLA.** `sla_deadline` is
computed once, at case creation, by `SlaCalculationService.
calculate_sla_deadline` and stored on the row. Reloading `case_sla_config`
(or the SLA service's in-memory config) changes what the *next* case gets,
never a case already open — see
`app/modules/cases/application/sla_service.py`'s module docstring.

## Known gaps

**PII at rest.** `case_evidence_item.evidence_data` (for the PII-bearing
evidence types — screening results, KYB results, onboarding evidence,
travel-rule data, Reactor investigations) and `compliance_case.
evidence_package` are documented as encrypted-at-rest. No field-level
encryption layer or KMS provider exists in the platform yet, so the columns
are unencrypted; this is the same platform gap `onboarding_request.
tax_identification_number` and `kyb_vendor_result.raw_vendor_response`
already carry, not a decision taken here.

**No cross-schema referential integrity on the case subject.**
`compliance_case.customer_id` / `.settlement_id` / `.onboarding_id` are bare
nullable UUIDs with no foreign key — the same trade-off `onboarding_case.
provider_route_id` already documents for a not-yet-existent table. A case can
reference a customer, a settlement, or an onboarding request across schema
boundaries, and this platform has no cross-module reference-integrity
mechanism for that yet.

**No read-only role.** This module has no `cases_ro` role or query service
yet (ARCHITECTURE.md constraints #10 and #15).

**`case_sla_config` has no target for `MANUAL`.** A manually-raised case has
no originating event to derive an urgency from, so `MANUAL` is deliberately
absent from both `sla-config.yaml` and the loader's completeness check. A
case created with `case_type = MANUAL` cannot go through
`SlaCalculationService.calculate_sla_deadline` until a future story decides
what policy (if any) applies — out of scope for S1T1/S1T2.
