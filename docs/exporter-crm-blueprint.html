01

Architecture

One rejected direction shaped everything here: a brand-new "exporters" module was proposed and turned down in favor of extending the module that already does most of this job. Three existing modules do the work; nothing new was created to hold it.

onboarding — where all new Exporter CRM code lives kyb — vendor adapters, generalized-not-replaced cases — review & decision engine, reused as-is
02

Design principles

Four rules a wireframe should never contradict — each one closes off a screen pattern that would misrepresent what the backend actually does.

01

One check-trigger form, any check type

KYC on a director, KYB on the business, a bank-statement check — all go through the identical form and the identical call. A screen with a different flow per check type would misrepresent the backend; there is exactly one.

02

Provider is shown, never invented

A result's provider field is whatever the adapter actually reported — "RXIL" stays "RXIL" everywhere it's displayed. No screen should imply the platform ran a check it only ingested.

03

A proposer can't be the approver

Case resolution is a hard two-person rule at the API level. The "Decide" action should be visibly disabled for whoever proposed it — not just rejected after the click.

04

The CRM shell and the verification journey are separate

An exporter can exist as a bare lead with just a name and country — no registration number, no address, no OnboardingRequest fully filled in yet. A screen shouldn't demand full KYB-grade detail to save a first contact.

Data model

What a screen actually reads and writes. Fields named here exist on the real entity — nothing invented for the sake of a mockup.

onboarding

ExporterProfile

  • customer_id — the enduring identity
  • gstin / pan / iec
  • source — immutable once set
  • relationship_manager
  • lifecycle_status
onboarding

Contact · Activity

  • name / role / email / phone
  • is_primary_contact — one per exporter
  • activity_type — call / meeting / note / task / follow-up
  • due_at — queried across all exporters
onboarding

  • legal_name · incorporation_country — required
  • registration_number · registered_address — optional at lead stage
  • status — 18-state journey
  • risk_rating · screening_result
onboarding

VerificationResult

  • verification_type — KYC, KYB, bank, vessel…
  • entity_type / entity_reference — what was checked
  • provider · status · risk_level
  • reviewed_by / review_status — immutable once set

  • case_type — onboarding_intake → onboarding_review
  • sla_deadline — null until review stage
  • resolution_action / resolution_note

  • evidence_type — 17 types, incl. RXIL-specific
  • source_epic — free text, e.g. "RXIL"
  • is_key_evidence
  • occurred_at — append-only
04

Personas

Four roles, mapped to the actual actor_type values the backend records against every action.

RM

Relationship Manager

Adds exporters, logs contacts and activity, moves cards through the pipeline. Lives on the CRM shell — rarely touches verification directly.

Op

Ops / Onboarding

Starts the real verification journey, collects documents and UBO declarations, triggers whatever checks are needed.

Co

Compliance

Reviews verification results one by one, and works the case queue — assigning, investigating, adding notes.

De

Decision-maker

Decides a proposed resolution — approve or reject. Enforced by the backend: can never be the same person who proposed it.

User journey

Two ways an exporter enters, one shared path to a decision. Every step names the real call behind it.

Thread A — Sales-sourced
1
RM adds an exporter

Just a name and country — nothing more required.

create_lead
2
RM logs the relationship

A call, a note, a follow-up with a due date.

add_contact · log_activity
3
Pipeline moves forward

Lead → Contacted → Data Collection, as things progress.

transition_lifecycle_status
4
Ops fills in the rest

Registration number, address, entity detail — once known.

submit_entity_details
5
Ops triggers checks

KYB, director KYC, bank statement — same form, every time.

POST /verifications
Thread B — RXIL-sourced
1
RXIL package arrives

KYB, AML, invoice-duplication, vessel, buyer rating — already done upstream.

stub batch adapter
2
A case opens automatically

onboarding_intake — a holding state, no SLA pressure yet.

case_type = ONBOARDING_INTAKE
3
Evidence accumulates

Each result tagged with its real source — never relabeled.

add_evidence_item
4
Case flips to review

Only now does the SLA clock start.

transition_case_to_review
Both threads converge

Review, decide, close

6
Compliance reviews results

Accepted, rejected, or escalated — per check.

POST /verifications/{id}/review
7
Case gets worked

Assigned, investigated, notes added.

assign_case · add_case_note
8
Resolution proposed & decided

A different person must decide it.

propose_resolution / decide_resolution
9
Exporter status reflects it

Compliance Review → Onboarded, or closed.

transition_lifecycle_status

Relationship Manager

Add exporter

A lead can be captured with almost nothing known yet.

Requires

Optional here
  • Registration number, registered address — filled in later
Endpoints
POST /onboarding/exporterscreate_lead
✓Resolved gap — previously there was nowhere to store a name before a full onboarding record existed. A lead now creates a minimal, searchable record in one step.
SCREEN 03
All roles

Exporter detail

Everything about one exporter, in one place — the screen every other action returns to.

Shows
  • Profile — GSTIN/PAN/IEC, source, stage
  • Contacts and activity history
  • Every verification ever run
  • Linked cases and their status
Actions
  • Log activity · add contact
  • Transition stage
  • Trigger a check
  • Start / continue onboarding
Endpoints
get_profile_detail get_onboarding_detail GET /verifications?entity_reference=

Widget-per-check-type layout (gauge for a match %, badge for pass/fail) reads well for the verification section here — see the reference screen shared for this build.

SCREEN 05

Scope boundary

What a wireframe should not include yet — each row is a deliberate decision, not an oversight.

CapabilityStatusWhy
Exporter CRM (profile, contacts, activity, pipeline)LiveBuilt and tested — this document's core.
Generalized verification triggerLiveOne mechanism, any check type — proven, not aspirational.
Case review & maker-checker decisionLiveReused from the existing cases module as-is.
RXIL ingestionStubBatch shape proven; real integration waits on RXIL's own confirmed spec.
Decentro / other real vendor adaptersStubOnly a placeholder exists — Middesk and Trulioo are the only live vendor integrations today.
Financing opportunity, buyer, invoice, shipment as entitiesNot builtExplicitly deferred — no financing decisioning exists yet.
Credit approval workspaceNot builtSits downstream of financing opportunities, which don't exist yet.
Ledger accounts, paymentsOut of scopeDeliberately held off until underwriting exists.
